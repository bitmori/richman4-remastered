# 002：原版存档的可移植、无损编解码

状态：**已迁移文件边界和一组明确的状态字段；整个存档恢复逻辑及游戏规则尚未迁移。**

## 来源与适用范围

依据本地上游提交 `ec7d70e693059d1e781d9d1cc2ad7f36d360d39e`：

- `asm/rich4_save_files.asm` 的 `_rich4_save_game_to_file`、`_rich4_load_game_from_file`：文件区域顺序、长度、签名、动态快照。
- `asm/rich4_player_info.h`：104 字节玩家记录中的明确字段。该文件由 Iru Cai 编写，GPL-3.0-or-later。
- `asm/rich4_config_file.h`：日期为日、月、16 位年，不能把四个字节直接当时间戳。
- `asm/rich4_map.h`、`asm/rich4_load_map.asm`：地图表的相对偏移、记录大小和从 1 开始的有效记录索引。
- `docs/saveload.txt`：玩家、卡片、道具的偏移交叉核对。

实现仅接受原版写出的 `0x00000026` 签名。这个签名的含义尚未推断为版本号。其他版本如果存在，需要单独研究布局。

上游原版读取时直接 `fread` 到含 32 位指针的内存结构，再修复人物名字、股票名字、地图及快照指针。本实现按小端字节显式读写，**不使用结构体布局、`sizeof(player_info)`、主机字节序或序列化地址访问内存**。数值采用固定宽度类型，容器和偏移计算采用适合主机的索引及经检查的 64 位算术。源代码和测试以 GPL-3.0-or-later 提供。

## API 与已经迁移的行为

`include/rich4/save.hpp` / `src/save.cpp` 提供：

- `SaveFile::decode(span)`：验证完整文件结构并持有输入字节的独立副本，异常类型为 `SaveError`。
- `header()`：日期、地图、阶段、玩家数量、人类玩家数量、当前玩家、初始资金和物价指数。
- `player(slot)`：玩家身份、位置、移动方式、操控标志、财务、点券、15 个卡片槽和 15 类道具数量。玩家 ID 是原有数组的零起始索引；`character` 是人物编号，二者不同。
- `map_summary()`：地图块大小、五个表的数量/偏移/步长。第五表语义未明，明确命名 `raw_reserved_table_4`。
- `regions()`：完整、连续、不重叠的文件区域目录；区分完全解码、部分解码和原始保留区。
- `encode()`：返回完整存档字节。没有字段变更时，与输入逐字节相同。
- `set_cash(slot, int32_t)` / `set_bank_balance(slot, int32_t)`：只修改对应字段的四个小端字节，支持完整有符号 32 位值域。

现金/存款 setter 是**存档字段编辑 API**，不承担游戏交易、限额、破产或利息规则，也不会同步修改历史快照。非法玩家索引抛出 `std::out_of_range` 且不改变任何数据。只有 `player_count` 内的玩家可读取或修改；原文件仍然固定保留四个玩家槽。

## 文件布局

所有数字都是文件中的小端数值，偏移以十六进制表示。下列「保留」指字节完整保存，不意味着已经实现其玩法语义。

| 文件偏移 | 长度 | 含义与覆盖范围 |
| --- | --- | --- |
| `0x0000` | 4 | 签名 `0x26` |
| `0x0004` | 4 | 日 u8、月 u8、年 u16 |
| `0x0008` | 2 | 地图编号 |
| `0x000a` | 2 | 阶段编号 |
| `0x000c` | 4 | 玩家数量，包含已破产玩家 |
| `0x0010` | `4 × 0x68` | 玩家记录，部分解码；其余字节原样保留 |
| `0x01b0` | 4 | 人类玩家数量 |
| `0x01b4` | `5 × 0x10` | 特殊玩家原始保留区 |
| `0x0204` | `46 × 0x18` | 地图对象原始保留区 |
| `0x0654` | `4 × 15` | 各玩家卡片 ID 槽，逐字节读取 |
| `0x0690` | `4 × 15` | 各玩家道具数量，逐字节读取 |
| `0x06cc` | 30 | 剩余卡片数量原始保留区 |
| `0x06ea` | 8 | 剩余道具数量原始保留区 |
| `0x06f2` | 4 | `ref_00499100` 原始保留区 |
| `0x06f6` | `0x1b00` | `ref_00497328` 原始保留区 |
| `0x21f6` | `48 × 8` | 玩家持股原始保留区 |
| `0x2376` | `12 × 0x24` | 地图股票原始保留区，包括历史名字地址 |
| `0x2526` | `28 × 12` | `ref_004967e0` 原始保留区 |
| `0x2676` | 4 | 当前玩家 |
| `0x267a` | 16 | 四个未解码全局字段，各自保留源符号名字 |
| `0x268a` | 4 | 初始资金 i32 |
| `0x268e` | 4 | 物价指数 i32 |
| `0x2692` | `0xb5` | 未解码全局字段；`regions()` 按每次原始写入单独标记 |
| `0x2747` | 4 | 主地图块字节数 `M` |
| `0x274b` | `M` | 主地图：40 字节表目录 + 原始地图记录 |
| `0x274b + M` 起 | `P × (0x2718 + M)` | 每玩家 10008 字节状态快照及 M 字节地图快照，全部原样保留 |
| 约定结构结束后 | 任意 | 若有额外尾部字节，以 `raw_reserved_trailing_bytes` 保留 |

完整已知布局的最小文件长度为 `0x274b + M + P × (0x2718 + M)`。`decode()` 验证每块都存在，包括每个快照；接受附加尾部字节但不解释它们。它不会把缺失文件后半部误当成合法的「只有头部」存档。

### 玩家记录中的明确字段

下列偏移相对于 `0x10 + slot × 0x68`：

| 记录内偏移 | 类型 | 解释 |
| --- | --- | --- |
| `+0x00` | 4 个保留字节 | 历史名字地址；绝不转换为主机指针 |
| `+0x04` | u32 | 玩家颜色 |
| `+0x08 / +0x0a` | u16 | x / y 位置 |
| `+0x0c / +0x0e` | u16 | 当前 / 上一地图节点 |
| `+0x10 / +0x11 / +0x12` | u8 | 方向 / 交通方式 / 骰子数 |
| `+0x13 / +0x14` | u8 | 人物编号 / 原版性别字段 |
| `+0x15` | u8 | 操控标志，低两位 0 停用、1 人类、2 电脑；位 2 为托管 |
| `+0x16..+0x1b` | 6 个保留字节 | 本次未解码 |
| `+0x1c` | i32 | 现金 |
| `+0x20` | i32 | 银行资金，原格式包括特别融资 |
| `+0x24 / +0x28` | i32 | 贷款 / 特别融资 |
| `+0x2c..+0x2f` | 4 个保留字节 | 本次未解码 |
| `+0x30` | u16 | 点券 |
| `+0x32..+0x67` | 54 个保留字节 | 各类状态天数、敌意及未明字段；本次未解码 |

卡片和道具不在玩家记录内部，分别在全局数组 `0x654 + slot × 15` 和 `0x690 + slot × 15`。未知、未实现及未使用玩家槽的内容都保留。

### 地图目录

地图开头连续五组 `(u32 count, u32 relative_byte_offset)` 对应节点、普通土地、设施、上市企业和第五个未明表；记录步长依次为 40、52、56、52、28。所有偏移都相对于主地图块起点，不能解释为内存地址。原版的有效索引从 1 开始，各表实际保存 `count + 1` 条记录，含索引零。

本实现验证表不能覆盖 40 字节目录、表完整位于地图块内，且表之间不能重叠；用 64 位算术计算 `(count + 1) × stride`，防止特制数量字段溢出。尚未解码地图记录内的所有字段，也没有验证道路连通性或恢复地产逻辑。

## 等价性证据

测试文件 `tests/save_tests.cpp` 的所有样例都是现场生成的合成字节，不含商业游戏素材或存档。

1. 从固定偏移构造日期、身份、财务、位置和卡片/道具，检查 API 逐项读取一致。
2. 未解释区使用非零、变化的字节填充，验证 `decode → encode` 完全相同；验证每一个文件字节都属于一个命名区域。
3. 对每个玩家测试 0、-1、一般值、`INT32_MIN`、`INT32_MAX`，独立构造预期输出，确认 setter 仅改变约定四字节。
4. 对单玩家合成文件的**每一个截断前缀**验证拒绝；测试错误签名、无效玩家索引、非法数量、短地图、地图越界及重叠表。
5. 输入首地址故意错开一个字节，验证不依赖对齐；验证额外尾部字节和历史指针 `0xffffffff` 都无损保存且不解引用。
6. 2026-10-05 在 macOS ARM64 使用 Clang C++20、`-Wall -Wextra -Wpedantic -Wconversion`、AddressSanitizer 与 UndefinedBehaviorSanitizer 编译并全部通过，没有诊断。

只读检查了当前 Wine 安装的两个存档，均为 89871 字节、4 位玩家、主地图 7956 字节、103 个节点、50 块普通土地、4 个设施、3 个上市企业和 21 条第五表记录。二者经过完整编解码后逐字节相同：

| --- | --- | --- | --- |
| `SAVE0.DAT` | `cbb8685e59abfeb8b8d5b4823d8a094ebb07d11dd9d121586b445dffb8ed6986` | 2026-10-06 | 98000 / 100000 / 21 |
| `SAVE1.DAT` | `d0b465c211389f30e3564dd5c7a94a6e3d8bed97dad2739841a7ab89e21d6b38` | 2026-10-05 | 98000 / 100000 / 55 |

## 尚未证明的内容与后续工作

本次等价性证据证明的是**明确字段映射及文件字节保持**，不是整局游戏行为等价；尚未用改过的存档进行原版游戏载入验证。未迁移对象、股票、各类状态效果、快照恢复或人物资源重建，也没有提供任意创建新存档的 API。原版载入后按系统时间重新播种随机数，因此单凭相同存档不能保证原版后续骰子/AI 序列相同，未来规则差分验证必须控制随机源并记录输入。

后续每迁移一个领域，先为其保留区建立字段定义和原版行为对照，再扩展类型/API/测试。主机内存模型应使用对象 ID 与容器引用；为了保持原存档兼容而保存的历史 32 位地址字节，不能重新成为新运行时的依赖。
