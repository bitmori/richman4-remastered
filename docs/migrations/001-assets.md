# 001 — MKF 资源、解压与 SPR/SMP 元数据

状态：已实现独立的可移植 C++20 模块。它是原生移植的资源基础，尚未接入完整游戏回合，不能据此声称整个游戏已经原生运行。

## 来源与范围

## 文件与接口

- `include/rich4/assets.hpp`：稳定的公开值类型与读取接口。
- `src/assets.cpp`：读取、解压、图像元数据解析。
- `src/assets/distance_tables.inc`：不可变距离前缀常量。
- `tests/assets_tests.cpp`：独立测试入口，不需要原版游戏资源。

```cpp
rich4::assets::Archive archive("Data.mkf");
const auto& info = archive.metadata(0);
auto bytes = archive.decode(0);
// 仅对签名为 SPR\0 / SMP\0 的资源调用：
auto graphics = rich4::assets::parse_graphics(bytes);
```

`Archive` 拥有输入字节，既可由路径构造，也可接受 `vector<uint8_t>`，便于 Android 的文件导入层和内存测试复用。`metadata` 返回文件中的固定宽度字段；`decode` 返回资源原始解压结果。图像条目记录 `int16_t` 宽高和原点、`uint32_t` 数据长度、主机 `size_t` 字节偏移，绝不把文件里的 4 字节字段替换成指针。

## 去除的架构依赖

| 旧实现 | 本次处理 |
|---|---|
| 直接把文件字节转成 `uint32_t*` 或图形结构体 | 显式逐字节读取小端整数，无未对齐访问、结构体填充或宿主字节序假设 |
| `gdata` 在磁盘中是 4 字节长度，载入后改写为指针 | 文件字节保持不变，另存具名的偏移和长度；64 位指针不会改变磁盘结构 |
| 解压状态是全局 `gtables` | 每次解压独立拥有状态，支持并发解压和多个档案 |
| 树中的索引以 16 位数组字节偏移保存 | 显式数组下标；321 个符号、641 个树节点，父链接数组包含符号节点 |
| 访问 `tab3` 尾部实际越入相邻 `tab4` | 合并成合法的父链接数组，不依赖两个结构成员相邻或越界行为 |
| 每次取压缩位预读未对齐的 32 位整数 | 按需逐位读取，严格限制在压缩输入内 |
| 载入时按 DirectDraw 像素格式修改资源 | 解压输出保持原始字节；颜色转换由独立渲染层负责 |
| 固定 16 槽全局文件句柄表 | RAII 容器，档案数量由调用方资源预算决定 |

新模块不包含 Windows 头文件、平台 API、ASM、整数与指针互转或对 32 位进程的要求。

## 保持的原版行为

1. MKF 第一项是文件末尾索引表的位置；每个索引项独立指定资源头位置，不强制索引递增，也不自行重排。
2. 原始长度等于存储长度时直接返回原始数据；不相等时使用 Rich4 的自适应字面值与回溯解压。
3. 每个字节最低有效位先读；保留树的初始权重、同权重交换顺序、根权重 `0x8000` 时的重标定顺序。
4. 回溯允许读到同次复制刚写出的字节；不能替换成 `memcpy` 或 `memmove`。
5. SPR 的首个图形位于 `start_offset + 512`，之前的 512 字节是原始 16 位调色盘；SMP 首个图形直接位于 `start_offset`。后续偏移按前项 `gsize` 累加。
6. 宽高、原点的 16 位有符号值保留；不依据宿主指针大小重算表长，不修改像素值、文本字节或调色盘。

`parse_graphics` 只解析元数据和数据范围，尚不解释 SPR 绘图命令，也不假设每项 `gsize == width * height * 2`。图像解码及绘制规则需要各自迁移和验证。

## 明确的行为变化

这些变化只针对损坏、矛盾或超过调用方预算的输入，不作为正常游戏行为的替代：

- 档案截断、非法索引、图像数据越界、表与数据重叠、压缩回溯早于输出起点等情况，抛出 `AssetError`。
- 压缩结束标记在声明的输出长度之前出现时抛错；旧函数会直接返回，留下未初始化的输出尾部。未初始化字节没有可移植的行为可以保留。
- 输出达到声明长度时停止，最后一个匹配过长时截断。这沿用**上游 C 还原版**的有界接口；原 EXE 没有长度参数，只相信结束标记。不能把损坏流的这种安全修正描述为原 EXE 行为；正常全资源的输出已经逐字节验收。
- 默认每项解压输出上限为 256 MiB，调用者可显式调整；分配输出前检查该上限。
- 图像签名必须是完整 `SPR\0` 或 `SMP\0`，不把仅前三字节相同的其他数据认作图像。
- 支持仅有 4 字节、索引位置为 4 的零条目档案，以及合法的零长度资源；不必为此触发越界读取。

`Archive` 当前把完整档案载入内存。它简化生命周期并便于一致性检查；Android 接入时若内存测量表明需要，可另行实现流式存储后端，保持当前解析和解压接口语义。

## 验证与证据范围

不含游戏素材的测试覆盖：

- 固定压缩向量：字面值、非 1 回溯距离、重叠回溯、尾部匹配截断。
- 65,000 个字面值的固定压缩输入，跨越多次频率重标定。
- 空输入、逐字节截断、非法回溯、提前结束标记、输出分配限制。
- MKF 索引/头部/负载/图像元数据边界与空条目。
- SPR/SMP 的有符号字段、调色盘位置、累计图像偏移、源数据不可变。
- 两个线程反复并发解压，以及 2,000 组有界、确定性的畸形输入。

在 macOS ARM64 上以 C++20、`-Wall -Wextra -Wpedantic -Wconversion`、AddressSanitizer 和 UndefinedBehaviorSanitizer 编译并通过。可独立复现：

```sh
clang++ -std=c++20 -Wall -Wextra -Wpedantic -Wconversion \
  -fsanitize=address,undefined -fno-omit-frame-pointer -Iinclude \
  src/assets.cpp tests/assets_tests.cpp -o /tmp/rich4-assets-tests
/tmp/rich4-assets-tests
```

另已完成原版 EXE 机器码 oracle v2 的全资源验收：独立的 32 位测试适配器在隔离 Wine 环境映射用户的原版 `rich4.exe`，调用 `0x455040` 解压函数；它没有用新实现或上游 C 解压器生成预期结果。输入是本机 7 个原版 MKF，EXE SHA-256 为 `5a90aee28ee5f7a5c3ba5cb935c9e55751a529c25fcd91208748a66293569550`。结果为 **2,673 项、296,005,111 字节逐字节一致，0 项差异**，其中 462 项压缩、2,195 项非空未压缩、16 项空资源。

机器码适配器通过合成 `ABC + EOS`、已知图像签名、两种输出预填值及越界哨兵自检，防止只复制压缩数据或产生未完整写入的结果。早期 v1 适配器被错误优化成原始复制，其结果已作废；仅 v2 通过结果可用于本次迁移验收。完整哈希、输入清单和逐项结果在本地 `.local/oracle/latest/manifest.json`，本次对照报告为 `.local/oracle/native-1791173237938583000/comparison.json`；可通过 `scripts/run_asset_oracle.py` 重新生成。参考机器码只在验证路径运行，不是原生运行时依赖。

上述全量比较证明当前这组资源的解压结果一致，不能证明全部游戏行为。图形命令、透明色、调色盘和绘制的正确性仍须各自比对；仅识别 SPR/SMP 结构不能替代渲染验收。

下一阶段需要分别验证图像命令/透明色/调色盘、文字、渲染时序和游戏逻辑，不能用资源一致性代替画面或回合行为一致性。
