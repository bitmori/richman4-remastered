# 007 — GND 地面资源与定点四边形绘制

状态：GND 资源解析、俯视纹理还原、原版单 tile 四边形光栅化已迁移至 C++20。18 张原版机器码生成的 640×480 金标画布逐像素完全一致。完整地图相机、场景排序、人物和建筑遮挡仍未迁移，本模块不代表完整地图画面已完成。

## 来源与范围

参照上游 `mytbk/rich4` 提交 `ec7d70e693059d1e781d9d1cc2ad7f36d360d39e` 的地面加载流程，以及 `asm/rich4.asm` 的原版函数：

- `0x45596a`：生成边的扫描线范围与纹理坐标。
- `0x40829d`：地图相机调用者，仅用于理解资源与角点来源；本次未迁移该完整函数。

派生实现沿用 `GPL-3.0-or-later`。原版 EXE 和 MKF 不加入仓库；金标纹理与调色盘由测试适配器生成，不含商业图片。

文件：`include/rich4/terrain.hpp`、`src/terrain.cpp`、`tests/terrain_tests.cpp`。

## GND 文件布局

所有整数按小端读取，文件字段不映射为主机结构体。

| 位置 | 内容 |
|---|---|
| `0x00` | 完整签名 `GND\0` |
| `0x04` | `uint16 width_tiles` |
| `0x06` | `uint16 height_tiles` |
| `0x08` | `uint32 tile_count` |
| `0x0c` | `uint32 reserved`，保留原值 |
| `0x10` | 256 项 `uint16` 原始 RGB555 调色盘 |
| `0x210` | `width_tiles × height_tiles` 项 `uint16` tile 索引 |
| 索引表之后 | `tile_count × 1024` 字节，每项是 32×32 indexed8 纹理 |

本机 8 项 GND 已完整解析通过，均为 72×72 网格、5,184 个 tile。解析器并不硬编码 72，也不要求纹理数量等于网格数量；它检查每个索引是否落在真实纹理表中。`Ground` 拥有解析后的值和原始纹理字节，`tile(index)` 返回有长度的只读视图，不存在文件内指针重定位或 32 位结构尺寸假设。

`render_overview` 按索引将纹理平铺成俯视图：

```text
tile = tile_indices[(y / 32) * width_tiles + x / 32]
pixel = palette[tile_bytes[tile * 1024 + (y % 32) * 32 + x % 32]]
```

原版 72×72 资源得到 2304×2304 图像。它用于核对资源和地图内容，**不是游戏中的投影相机截图**。默认限制输出不超过 16 Mi 像素，调用者可调整预算。

## 四边形绘制接口

```cpp
rich4::terrain::draw_tile(
    canvas, ground.tile(tile_index), ground.palette,
    corners, clip);
```

`canvas` 复用 `graphics::Image`；四角点采用具名 `Point{y, x}`，顺序与原版一致。`clip` 的右、下边界不含在内。调色盘索引 0 也照常绘制，不采用人物 SPR 的透明规则。

原版把画布、纹理、调色盘、裁剪区、480 行边界及纹理坐标保存为全局状态。新版把这些依赖全部作为参数或局部值，按画布实际高度分配具名 `Scanline`。每次调用有自己的 scratch，互不共享；原始 640×480 stride 由画布宽度替代。

## 必须保留的整数规则

1. 四个顶点的纹理坐标是 `(0,0),(31,0),(31,31),(0,31)`，但四边纹理增量是 `(32,0),(0,32),(-32,0),(0,-32)`。不能以 31 替换 32。
2. 使用 16.16 定点数；有符号除法向零截断，取整数像素位置时按原版算术右移向下取整。
3. 当某个纹理步长为负，其起点的小数部分为 `0xffff`，否则为零；这影响边界采样。
4. 扫描边时，横坐标左、右界使用两个独立比较；纹理坐标究竟写入哪一侧，由原始边的 `dy` 正负决定，不能简单跟随刚更新的横坐标界。反向绕序金标专门验证这一点。
5. 垂直和水平范围都采用右端不含的循环；填充在首个未触及的扫描线停止。
6. 纹理采样为 `((v >> 16) & 31) * 32 + ((u >> 16) & 31)`，保留原版坐标回绕。
7. 加减和乘加通过 `uint32_t` 明确执行低 32 位回绕，再按位解释为有符号值；没有负数左移或有符号溢出的未定义行为。

## 输入范围与明确变化

- 画布尺寸须在 1–32,767 范围，像素存储须匹配尺寸；非空 opacity 存储亦须匹配。
- 角点字段为 `int16_t`；每条有向边的真实 `dy` 必须能用 `int16_t` 表示。超过该范围时拒绝，不重演旧代码将高度截断后错误排序或越界写入的结果。
- 裁剪区域与画布边界求交，避免原全局 clip 越界导致写出目标缓冲。
- GND 的非法签名、零尺寸、截断调色盘/索引/纹理和不存在的 tile 引用均抛错。尾部未使用数据不参与图像生成。
- 新版每次调用初始化所有 scratch。金标也显式初始化了原版 scratch；当前保证的是这套明确前置条件下的绘制结果。尚未对依赖旧 scratch 残留的畸形、自交四边形作兼容承诺。

## 验证结果

在 macOS ARM64 上以 C++20、`-Wall -Wextra -Wpedantic -Wconversion`、AddressSanitizer 和 UndefinedBehaviorSanitizer 编译并通过：

- 合成 GND 的小端值、调色盘、索引重排、完整纹理范围和俯视输出。
- GND 截断、索引越界、巨大纹理数量、输出预算和源数据不可变。
- 不透明索引 0、右下边界不含、局部 clip、空 clip、退化四边形、目标缓冲尺寸检查。
- 本机原版资源中的全部 8 项 GND 解析成功。
- **原版 EXE oracle v2 的 18 张 640×480 画布，共 5,529,600 个 16 位像素，逐像素一致，0 差异。**

原版画布覆盖 31/32/16/64 像素矩形、两种菱形、负坐标、右下截断、完全不可见、部分 clip、整屏、反向绕序和细长四边形。测试适配器使用合成纹理 `texture[y*32+x] = (x+y*7)&255` 和调色盘 `palette[i] = (i*0x123+0x11)&0x7fff`，直接调用 EXE 的 `0x4557a1`；新版输出不参与预期值生成。

```sh
build/native/terrain_tests .local/oracle/latest/golden/terrain.jsonl
```

金标文件、输入和适配器哈希见 `.local/oracle/latest/manifest.json`。这些测试证明覆盖案例的光栅化一致，不代表所有可能四边形已穷举，也不代表游戏相机、地图事件或回合逻辑已一致。

后续相机迁移应继续使用原版角点网格和遍历顺序验证；它们包含原始整数舍入，不能直接以简化投影矩阵替代并宣称逐像素一致。
