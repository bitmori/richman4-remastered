# 000：以原版 EXE 建立行为对照

状态：schema 2 原版 MKF 机器码批量导出与原生解码器 **2673 项逐字节比较通过**。
报告由 `scripts/run_asset_oracle.py --native-tool ...` 生成；这个结论只覆盖下面
明确列出的模块和输入，不代表完整游戏迁移完成。

## 为什么不用重编译版本当唯一标准

上游 C 代码已经是一次还原，可能与原始程序存在偏差。本工具直接映射用户本机的
v3.11 `rich4.exe`，调用其中原封不动的 x86 函数。没有重新实现一个“参考解码器”，
也没有把上游 C 产生的结果称为原版结果。Wine 与 x86 模拟仅用于测试；原生核心
不链接这些测试依赖。

原版 EXE SHA-256：
`5a90aee28ee5f7a5c3ba5cb935c9e55751a529c25fcd91208748a66293569550`。
脚本拒绝其他版本，避免拿固定地址调用错误函数。上游固定 revision 与入口地址
线索见 `THIRD_PARTY_NOTICES.md`；地址最终经过本机原 EXE 反汇编确认。

## 实现与隔离

`tools/oracle/original_mkf.c` 是一个很小的 MinGW x86 测试适配器。它本身链接在
`0x10000000`，通过 `LoadLibraryExA(..., DONT_RESOLVE_DLL_REFERENCES)` 映射原版，
检查其实际地址为 `0x400000`，并检查解压入口的指令前缀。不会启动游戏入口、
解析其导入或调用其界面、音频初始化函数。

每次运行使用新的隔离目录：

```text
~/Library/Containers/org.boxedwine/Data/Library/Application Support/Boxedwine/
  Rich4-oracle/<run-id>/root/      独立 Wine prefix
  Rich4-oracle/<run-id>/work/      独立 D 盘
```

只有运行时 ZIP 与现有安装共用，且只读。不会使用 `Rich4/root`、不会修改原始
Downloads 文件、游戏存档或正在玩的 Wine prefix。EXE 和七个 MKF 被复制到隔离
输入目录。`.local/oracle/latest` 指向最近一次成功运行的 `work`。

Git 中只保存适配器、脚本和文档；EXE、资源、导出字节和测试前缀均不提交。
适配器源码先复制到隔离目录再编译，并记录所有 C/header 哈希，防止并行编辑让
编译出的二进制与报告里的源文件版本不一致。测试进程关闭所有文件后直接结束自身，
不会让 Windows loader 对这个故意未初始化的 EXE 执行 detach 回调。

### 已发现并修复的 oracle 失效

2026-10-05 的最初 schema 1 捕获**无效，不可作为原版解压证据**。全量比较发现
462 个压缩条目全部不符；输出实际是压缩 payload 连同其后的文件字节，未压缩
条目则一致。检查本机 MinGW GCC 16.2.0 的 `-O2` 产物发现，适配器的压缩分支和
间接解压调用被消除了，只剩 `memcpy`。此处记录实际观察，不把原因未经最小复现
确认就归为编译器缺陷或原游戏行为差异。

修复包括：适配器采用 `-O0`，反汇编确认调用存在；运行独立编码的 `ABC` 加 EOS
合成流，验证得到 `ABC` 且尾部哨兵不变；已知 `data.mkf[0]` 必须解出 `SMP\0`；
最后再次全量逐字节比较。schema 提升到 2，旧 manifest 和完成标记一律拒绝。
2026-10-05 `20261005-120642-953000` 捕获及其对应 native 比较首次通过全部 2673 项。
这次失败说明 oracle 自身也必须自检，不能只凭“进程跑完”宣布对照成立。

## MKF 原始字节对照

| 项目 | 原版事实 |
| --- | --- |
| 解压入口 | `0x455040` |
| ABI | `cdecl(void *destination, const void *source)` |
| 停止条件 | 距离编码 `0xfff` 结束标记 |
| 固定表 | `0x483430`、`0x483530`，初始树 `0x483630` |
| 工作树 | `0x4847bc` 起，函数每次重新初始化 |
| 外部依赖 | 该函数及其内部子函数不调用 Windows API |

**原版解压函数没有输出长度参数。** 上游 C 的第三个参数和按输出长度停止是还原版
新增的边界，不能反过来假设原版也如此。适配器为原版预留输入末尾 4 字节，因为
其指令会做 32 位预读；此处不是声称原版对截断输入安全。

每个压缩条目用 `0xa5` 和 `0x5a` 两种目标预填值各解一次，要求输出完全相同，
并检查声明长度之后 4096 字节哨兵未被修改。因此提前结束而没有写满目标的情况
不会被默默当作正确输出。未压缩条目按格式直接复制，空条目保留零字节文件。

对照层级是 **解压之后、颜色转换和 SPR/SMP 指针重定位之前的字节**。在这个层级
比较不会被 32 位指针值、内存分配地址或屏幕像素格式干扰。索引读取由适配器按
文档执行；本工具并不声称测试了原版的文件 I/O 与索引 API。

本机素材有效捕获：7 个 MKF，2673 项，296,005,111 字节。其中 462 项压缩，
2195 项非空未压缩，16 项为空。各输入文件及各输出都有 SHA-256 记录。

原生 `rich4-tool dump` 输出同样的原始字节，Python 脚本逐项比较实际 bytes，并
另外检查原始输入及 oracle 输出没有在捕获后变化。报告保存 native 可执行文件
SHA-256、比较数量和差异列表。没有原版素材的 CI 可运行合成单元测试，但不能
假称重新执行了这些完整素材对照。

## 像素及 blit 对照

适配器还调用原版以下入口：

| 原版入口 | 测试 |
| --- | --- |
| `0x451801`；格式变量 `0x47637c` | 格式 0、1、2、3 各穷举全部 65536 个 16 位输入，同时检验单像素尾部路径与成对处理路径一致 |
| 普通 blit `0x455b3a` | 定位、四边裁剪、完全离屏、图像 anchor |
| 透明 blit `0x455c52` | 同上，并覆盖源像素 0 保留背景的行为 |

`golden/pixels-<format>.bin` 按输入 0…65535 顺序保存小端 16 位原版输出。
`golden/blit.jsonl` 保存 1344 组参数、返回值、42 个输出像素。固定目标 7×6，
初始颜色 `0x7bde`；源 5×4，像素 `i % 4 == 0 ? 0 : 0x101 + i`；anchor
取 `(0,0)`、`(-2,1)`、`(2,-1)`，放置坐标 x=-6…9、y=-5…8，分别测试
普通和透明两种模式。这些构造输入不是游戏素材。

范围限制：blit 此次不启用全局 draw-area，不覆盖缩放、调色板绘制、混色等其他
图形函数。源尺寸小于目标，避免把原版双侧裁剪的潜在越界行为作为新实现要求。

扩展捕获还包括 SPR 调色板图像（114 组）和 terrain 四边形（18 组）。SPR 直接
调用 `0x456512`/`0x45663e`，使用 synthetic 5×4 索引图，刻意设置 palette[0]
非零而 palette[1] 为零，以验证透明条件是**索引 0**而不是转换后的颜色 0。
输出 `golden/spr.jsonl` 保存全画布中相对背景发生变化的位置和颜色。

Terrain 直接调用 `0x4557a1`；18 个构造四边形覆盖矩形、菱形、斜边、反向顶点、
负坐标、画布边缘和局部 draw-area。目标 640×480，源纹理 32×32，调色板与纹理
完全由公式构造。`golden/terrain.jsonl` 记录 `{y,x}` 顶点及 clip；对应二进制保存
完整画布，防止只检查四边形内部而漏掉越界绘制。每组重新初始化原函数 scanline
工作区；这不是对完整摄像机、地形拼接或地图遮挡排序的验证。

`rich4-graphics-oracle` 链接实际 `rich4_core`，读取像素、blit、SPR golden 并比较。
原生接口的 blit 返回类型是 void，因此对照其像素状态，不给原版返回值增加新语义。

## 纯逻辑扩展

`original_logic.h` 捕获日期与方向，不调用系统时钟。`calendar.csv` 覆盖原版
1998-01-01 至 2200-12-31 的每一天，日期列按 `year<<16 | month<<8 | day` 的
uint32 十进制保存，包括 weekday、当月天数、推进一天、±400 天和日期差；前
400 天的 minus_400 记 0，测试应跳过，避免在定义范围之前取日期。另有 64 组
`calendar_packed.csv` 验证位级 packed 增量，包括非常规月日编码。

`direction.csv` 覆盖 [-128,128]² 全格点、2049 个整数比例的八个象限/交换组合，
以及 INT32_MIN/MAX 等 11×11 边缘组合，共 82,562 组。原版入口分别为日期
`0x451f8c`/`0x45201f`/`0x4520a6`/`0x452117`/`0x45218f`/`0x4521aa`/`0x4521cb`，
方向 `0x454fb4`。

`original_inventory.h` 由库存模块负责人维护，捕获 11,412 组卡片/工具纯逻辑状态
变化，包含原价格、同价和变化价格输入、库存字节回绕、不同玩家槽位。只使用
不会进入图形分支的交通状态。修改只发生在隔离进程内存并恢复，不修改原版 EXE。
该 corpus 已与原生库存实现全部逐字段一致，并通过 ASan/UBSan。

`original_economy.h` 捕获 4,705 组连锁店数量和地租计算，含不同 owner、Big5 街名
精确比较、等级与物价索引、空街名/NULL 的不同含义、32 位加法/乘法回绕，以及
65,538 块地的加法溢出构造。原版仅操作映像内注入的构造地图，捕获后恢复全局
指针；4705 组与原生逐字段匹配。它不证明支付、现金变动或事件触发已经迁移。

`original_random.h` 直接调用 Watcom CRT `rand` `0x456f2d` 和 `srand` `0x456f50`。
原函数通过 `0x488f4c` 的回调获取线程上下文；适配器提供独立 16 字节上下文，
只替换这个取址回调，不更改随机数算法。读取上下文 `+0xc` 处原函数写回的状态，
输出 `random.csv` 的 `seed,index,return,state`，12 个边界 seed 各调用 1024 次。
此捕获不使用重建的 LCG 计算期望值，也不调用 MSVCRT 的随机函数。所有序列显式
播种，因此不覆盖游戏 CRT 启动时的默认种子选择或骰子/AI 的调用次序。

已由原生逻辑测试验证日期 74,146 组、packed 日期 64 组、方向 82,562 组一致，
并通过 ASan/UBSan。图形 native oracle 验证 RGB565 65,536 组、blit 1,344 组、
SPR 114 组逐像素一致。Terrain 与 RNG 的最新验证结果见各自迁移文档，避免将
“生成了 golden”写成“消费 golden 的原生实现也已通过”。

## 运行

前置：按 README 准备本机 Boxedwine/Wine 和 MinGW；原版资源只需用户本机持有。

```sh
# 创建新的原版捕获；默认 game-assets
python3 scripts/run_asset_oracle.py

# 捕获并立即与原生工具逐字节比较
python3 scripts/run_asset_oracle.py --native-tool build/native/rich4-tool

# 使用最近一次捕获，重新验证新版原生工具（无需再次启动 Wine）
python3 scripts/run_asset_oracle.py --reuse-oracle --native-tool build/native/rich4-tool

# 验证原生普通/透明 blit、SPR 索引透明、颜色转换
build/native/rich4-graphics-oracle .local/oracle/latest/golden
```

失败不覆写最近一次成功捕获。查看该 run 目录下 `wine.log`；成功要求 helper 的
最终完成标记、允许的运行器退出码、全部输出大小检查同时成立。Boxedwine 某些
成功关闭路径返回 1，因此不能只依据进程返回码宣称测试通过。

这套对照证明的是**被运行的函数在记录的输入集合上的行为一致**，不是完整游戏、
所有合法压缩流或恶意损坏文件的证明。损坏资源应由原生实现的边界检查和 sanitizer
测试独立验证，不把不安全输入送给缺少边界保护的原版函数。
